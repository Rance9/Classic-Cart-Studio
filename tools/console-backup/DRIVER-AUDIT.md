# USB driver audit: Hakchi2 CE 3.9.3's console driver setup, and the Workbench path

Research date: November 15, 2026. Sections 1-6 are a read-only audit: nothing was executed, installed, staged, bound, removed or
changed on any PC; the pinned helper was examined as file bytes (its embedded programs were located and their signatures read, never
run), and the sources were read at the exact commits below. Sections 7-11 describe Workbench's own driver setup and removal as
implemented and tested through injectable seams and file-only artifacts (no driver, certificate or certificate store changed on any PC;
nothing run elevated); the real path is closed in code by `Gate.DriverChanges`. Updated November 16, 2026: the trust certificate is
kept until its package's removal is read back finished, with a later cleanup (section 9, "After the removal"), and section 12 separates
the trust routes and their x64/Arm64 prerequisites. The trust route is the owner's choice and is not chosen here.

Evidence labels: **verified** = read in the pinned source or measured on the pinned file's bytes; **believed** = follows from documented
Windows/SetupAPI behavior or strong indirect evidence, not observed here; **unknown** = not established.

## 1. How Hakchi 3.9.3 reaches the helper (verified)

- `WaitingFelForm.cs:13-31` `DriverInstalled()` runs `pnputil.exe -e` and returns true if the output contains `USB\VID_1F3A&PID_EFE8`.
  `pnputil -e` lists packages by published name, provider, class, date/version and **signer name**, not hardware IDs, so the match is on
  the signer `USB\VID_1F3A&PID_EFE8 (libwdi autogenerated)` (**believed**; consistent with the project's recorded install, execution log
  1.7). Consequences: any package signed by a libwdi-generated certificate for that VID/PID passes, including a Zadig libusbK or libusb0
  package; the check never looks at device binding, backend or interface GUID.
- `WaitingFelForm.cs:33-56` `InstallDriver()` starts `driver\classic_driver.exe` with verb `runas`, working directory a new
  `%TEMP%\hakchi2-ce-temp[N]` (`TempHelpers.cs:8-58`), waits, returns the exit code, then deletes that folder (best effort, `:46-53`).
- `WaitingFelForm.cs:62`: the FEL wait dialog runs `InstallDriver()` **automatically** when `DriverInstalled()` is false. If Workbench
  removes the package, Hakchi's next FEL wait asks for setup again. The "Install driver" buttons: `WaitingFelForm.cs:104-114`,
  `WaitingShellForm.cs:71-75`.
- `tools/downloadfiles:23` downloads the binary from the `classic_driver_1` release; `hakchi_gui.csproj:2903` ships it as content.
  Hakchi's build does not compile it.
- Hakchi 3.9.3 contains no code that removes a driver package or a certificate (no `pnputil` other than the check above, no
  `DiUninstallDriver`, no certificate store access).

## 4. After a removal, what remains

Removing the package (`pnputil /delete-driver oemNN.inf /uninstall`, or `DiUninstallDriverW` on `C:\Windows\INF\oemNN.inf`) removes the
driver store copy, the published INF and its binding to devices (**believed**; Windows may need a restart). It does not remove: the
certificate in Root and Trusted Publishers (that needs its own removal by exact thumbprint); the two coinstaller DLLs in System32; the
WinUSB service display name; the Group Policy key; disconnected device instances' registry entries; `setupapi.dev.log` and event log
entries; temporary files or a key container left by a crash (**believed**). Package removal is therefore never proof that every trust
change or Windows record is gone, and the Workbench texts say so (`DriverText.RemovedLogsRemain`).

## 5. Windows inbox WinUSB without a new package

- **Microsoft OS descriptors in FEL mode: believed not exposed.** Windows does not bind WinUSB to `1F3A:EFE8` on its own; community
  guides for Allwinner FEL on Windows require assigning WinUSB with Zadig (for example
  [the xfel guide](https://w2.electrodragon.com/SDK-dat/Xboot-dat/xfel-dat/xfel-dat.md)). Not observed on a console here (no console
  contact is authorized). The FEL loader is mask ROM, so nothing CCS sends could add descriptors before the loader runs.
- **The clovershell gadget:** the CCS RAM image sets the console's legacy `android_usb` gadget to `1f3a`/`efe8`, function `clover`
  (`tools/console-backup/ram/ccs-init:26-34`, **verified**), the same hardware ID as FEL, so one association serves both modes. Whether
  that 3.4-era gadget answers Microsoft OS descriptor requests is **unknown** (believed not). Whether both modes appear as the same device
  instance on a port (no serial number) is **unknown**.
- **Device Manager "Universal Serial Bus devices > WinUsb Device":** binds inbox `winusb.sys` with no new package and no certificate,
  but Microsoft states it "doesn't add a device interface GUID"; the documented fix is a manual `DeviceInterfaceGUIDs` value under
  `Enum\USB\VID_…&PID_…\…\Device Parameters`, repeated for each physical port (**verified**, Microsoft Learn). LibUsbDotNet's WinUSB
  discovery needs that value (`LibUsbDotNet/Main/SetupApiRegistry.cs:130, 151-173`, **verified**), so this binding alone is not usable
  by the CCS transport. Workbench recognizes it (`AssociationKind.WinUsbWithoutInterface`) and changes nothing.
- **A custom INF-only WinUSB package** (no kernel binary, inbox `winusb.sys`) still needs a **signed catalog** to install (Microsoft
  Learn, **verified**). The signer must be trusted: either a new private trust root (libwdi's way, which the owner prefers to avoid) or a
  real code-signing signature. Whether a catalog signed through the Rance9 LLC signing account would be accepted for this on Windows 11
  (and on a managed PC with WDAC/HVCI) is **unknown**; Windows would show its own publisher prompt. No CCS kernel driver is needed in any
  case: the console only needs Microsoft's WinUSB with a registered interface.

## 6. What the CCS transport needs, and "no runtime helper extraction"

- **Verified:** CCS's FEL loader (`tools/console-loader/CcsConsole/Usb/LibUsbFelUsb.cs`) and clovershell pipe
  (`tools/console-worker/CcsWorker/Shell/LibUsbBulkPipe.cs`) open the console through `UsbDevice.AllDevices` / `OpenUsbDevice` of
  LibUsbDotNet, a managed assembly. The standalone Utility loads it from memory (`ccs-backup-utility/Program.cs:55-71`). Its native calls
  go only to Windows system DLLs: `winusb.dll` (`WinUsb/Internal/WinUsbAPI.cs:41-45`; `libusbK.dll` only when built with
  `USE_LUSBW_FOR_WINUSB`, and the shipped binary references `winusb.dll`, not `libusbK.dll`), `setupapi.dll`, `kernel32.dll`, `advapi32.dll`,
  `user32.dll`. The binary also names `libusb-1.0`, used only by its MonoUsb backend on Linux or when `ForceLibUsbWinBack` is set, which
  CCS never sets. The libusb-win32 path talks to `\\.\libusb0-NNNN` through `DeviceIoControl` (`LibUsb/Internal/LibUsbDriverIO.cs:35`).
  **No native backend DLL is shipped, extracted or needed at run time.**
- **Which associations work:** the WinUSB path finds any device whose `DeviceInterfaceGuids` is registered, whatever the GUID, so the
  pinned Hakchi association and another WinUSB association (for example Zadig's, random GUID) both work with the transport (**verified**
  in source; not tested with a console). libusbK's driver is not reachable through `winusb.dll` (**believed**). libusb-win32 is reachable
  through LibUsbDotNet's legacy path but CCS has never been tested with it. Workbench therefore treats these as different associations
  and reuses only WinUSB with an interface GUID.
- **One program at a time:** LibUsbDotNet notes that WinUSB devices "can't be shared by multiple processes"
  (`Main/DeviceLockType.cs:44`, **verified** in source; Windows behavior **believed**). Workbench and Hakchi cannot use the console
  together; the engine treats an open Hakchi as a reason not to remove the driver (`DriverUsage.OtherProgramsFromProcesses`).
- **Staging versus helpers:** Windows device installation takes an INF path on disk and copies the package into its driver store, so
  setting up a driver writes package files by nature. That is driver-package staging. The pinned helper is different: an unsigned
  executable that itself writes two more unsigned executables and four DLLs and runs them. Running it from the one-file Workbench would
  mean extracting an executable helper, which is not allowed. Running it where it already is on disk (the Hakchi package installed with
  Classic Cart Studio for Windows, hash-verified before use, as `tools/companion/hakchi_bridge.py:265-279` does today) is not extraction.


## 7. The Workbench path

1. **Offline work never reaches the driver code.** Browsing, export and repair of backup files need no USB.
2. **First console action:** read the PC without elevation (`WindowsDriverStore`, `DriverSetup.Assess`). Reuse, change nothing and record
   it as pre-existing when the console's identity has the pinned Hakchi association (bound or only staged: a staged package is
   pre-existing even with no console connected), Workbench's own package from an earlier setup, or another WinUSB association with a
   registered interface. Text: "Workbench used a USB driver already on this PC. It will leave that driver in place."
3. **Never replace another association.** libusbK, libusb-win32, WinUSB without an interface or any other driver bound to (or staged for)
   the identity is explained and left alone.
4. **Setup only when nothing is there**, with Workbench's own data-only package (section 9), never the pinned helper: the one-file
   Workbench cannot extract or run that unsigned executable, and it deletes certificates by subject (section 3, 3a). The PC changes are
   listed before consent (`DriverText.CcsPackageChanges`, the trust certificate included).
5. **Before and after every change**, record the PC state in the chosen workspace (`DriverLedger`) and judge the result only from the
   state read back, never from the exit code.
6. **Removal at close only when eligible** (`Eligibility`): exactly the recorded `oemNN.inf` (no `/force`, no hardware-ID or subject
   deletion; `DiUninstallDriverW`, which reports a needed restart), then each certificate the setup added, by exact thumbprint and store,
   only once the package is read back gone and not waiting for a restart, and only if unchanged and signing no other package; otherwise
   the certificate stays and a later cleanup is recorded (section 9). Restarts are never automatic and a pending removal is never called
   finished.

## 8. Is a self-made catalog with an owned certificate required? (documentation)

The question: for an INF that only references Windows' in-box WinUSB (no driver binary of its own), on the Windows versions Workbench
supports (Windows 10 and 11, x64 and Arm64), can the package be installed without a catalog signed by a certificate the PC trusts?

| Source (Microsoft Learn, docs commit `81d06fd79dd36cdd74ec0b3aeed6c4e52c2e2fc3` unless noted) | What it says |
|---|---|
| "WinUSB (Winusb.sys) Installation for Developers" (ms.date 2025-03-26) | The universal WinUSB INF (Include/Needs `winusb.inf`, `WINUSB.NT`, `WINUSB.NT.Services`, `DeviceInterfaceGUIDs` by AddReg, no co-installers) and: "Create a signed catalog file for the package. This file is required to install WinUSB on Windows." The only package-free route is Device Manager's manual "WinUsb Device" pick plus a hand-added `DeviceInterfaceGUIDs` value, repeated per physical port (section 5). |
| "PnP Device Installation Signing Requirements" (ms.date 2022-03-03) | "These signing requirements need to be met in order for the driver package to be staged to the Driver Store." Release: the catalog "must be signed by WHQL or signed by a third-party release certificate". Development and test: "a driver must have a WHQL test signature or must be signed by a test certificate". "Windows 10 in S mode and editions for architectures other than x86 and amd64 require catalog files for driver packages signed for release to have been signed by WHQL." |
| "Driver Signing Policy" (ms.date 2024-08-19) | Kernel-mode code signing rules (Windows 10 1607+: new kernel drivers signed through the Dev Portal) apply to driver binaries; "In addition to driver code signing, you also need to meet the PnP device installation signing requirements". Workbench's package has no binary: `winusb.sys` is Windows' own, already signed by Microsoft. |
| "Installing Test Certificates" (ms.date 2020-07-20, docs commit `8e191d82105b0e1878725ffc06550842fd51b8af`) | To install a test-signed package "the test computer must have the certificate for the certificate authority (CA) that issued the package's test certificate installed in the computer's Trusted Root Certification Authorities certificate store", the local machine store. |
| "Signature Categories and Driver Installation" (ms.date 2021-12-03) | A package signed by a trusted publisher (Trusted Publishers) installs without a prompt; "publisher of unknown trust" prompts administrators; standard users are never prompted and anything not trusted is refused. |
| `DiInstallDriverW` / `DiUninstallDriverW` (newdev.h; docs commit `fa53641576e3603fa7b66d3a4ad969d3ce49d6f3`) | Flags 0: install only where the package is the better match (`DIIRFLAG_FORCE_INF` "can result in replacing a more compatible or newer driver"); `NeedReboot` supplied means "the caller must prompt the user to restart"; `ERROR_IN_WOW64` for a 32-bit caller. `DiUninstallDriverW` (Windows 10 1703+) reinstalls affected devices with another match or the null driver, then removes the package from the store. |

**Answer (implemented): yes.** An INF-only package must still be staged through the driver store, and staging requires a catalog signed
by WHQL, by a commercial (third-party release) certificate, or by a test certificate whose issuer is in the PC's Local Machine Root store.
Workbench has no WHQL signature and no commercial driver-signing route today (sections 11 and 12), so the setup makes its own certificate,
adds it to Root (required to verify) and Trusted Publishers (so Windows does not stop the elevated, window-less step with a publisher
prompt), and signs the catalog with it. That is what libwdi does too; what Workbench does differently is in section 9. Microsoft
describes adding a publisher's certificate to Trusted Publishers to automate installation as a practice for internal test systems only,
never for a driver package distributed outside the organization (section 12, route a): this route is implemented behind the closed
boundary so it can be reviewed and tested, and it is **not** a chosen public route.

Corroborating evidence on this PC (**verified**, read only): the owner's Hakchi setup on 2026-10-09 staged `oem206.inf` signed by a
libwdi self-made certificate on this Windows 11 x64 PC (execution log 1.7), and the `driver-real` group reads it there today
(assessment `PinnedHakchi`). The application's own code signature (Rance9 LLC, when signing is set up) is not evidence that a driver
catalog is accepted: Authenticode on the executable and the PnP catalog check are separate decisions.

## 9. What Workbench sets up (implemented; closed by the DriverChanges boundary)

**The package** (`CcsBackup/Driver/CcsDriverPackage.cs`, **verified** by the `driver-package` group on file bytes in its work folder):

- `ccs_console_usb.inf`, ASCII, fixed text in code (SHA-256 `da4aacda41f0ec77…`, the constant `CcsDriver.InfSha256`): `Class=USBDevice`,
  Provider `Rance9 LLC`, `PnpLockdown=1`, models for NTx86/NTamd64/NTarm64 naming only `USB\VID_1F3A&PID_EFE8`, Include/Needs
  `winusb.inf` `WINUSB.NT` and `WINUSB.NT.Services`, and one AddReg: `DeviceInterfaceGUIDs` = `{FBA1B326-D7E7-4546-9933-75C8B24ED040}`
  (Workbench's own GUID; the transport finds any registered GUID, section 6). No CopyFiles, AddService, co-installer, ClassInstall32,
  deletion or registration: compared with section 3, no System32 files, no WinUSB service rename, no Group Policy change.
- `ccs_console_usb.cat`: made by Windows' own catalog functions (wintrust `CryptCATOpen` CREATENEW, `CryptCATPutCatAttrInfo` HWID1/OS,
  `CryptCATPutMemberInfo` with the INF's SHA-1 as tag, flat-file subject type, the `<<<Obsolete>>>` SPC link, `CryptCATPutAttrInfo`
  File/OSAttr, `CryptCATPersistStore`), the same calls as pbatard/libwdi `30df0c0e051b0132c4b9ebed8c054bc8eb3aaaec` `libwdi/pki.c:1096-1206,
  1310-1400` (`AddFileHash`, `CreateCat`); then signed as CMS with SHA-256 (`SignedCms`, signed attributes contentType, messageDigest,
  SpcSpOpusInfo, SpcStatementType individual).
- **The certificate** (`CcsSigner`): new for every setup; subject `CN=CCS Console Workbench USB driver (1F3A-EFE8) <operation id>`;
  RSA 3072 in an unnamed CNG key (never persisted; the test counts the user's and the machine's key folders before and after);
  BasicConstraints CA=false (critical: it can issue nothing, unlike libwdi's certificate, which has no BasicConstraints), KeyUsage Digital
  Signature and EKU Code Signing only (both critical); SHA-256; valid until 2099-12-31 because Windows checks the package again whenever
  it sets the console up on another USB port and nothing is time-stamped (no network). The key is destroyed before anything on the PC
  changes; only the public certificate is added to the stores.
- **Read back by Windows** (`driver-package`, **verified** on this PC, nothing trusted or installed): Windows' CMS reader verifies the
  signature; Windows' catalog reader lists one entry with the INF's SHA-1 and its attributes; `CryptCATAdminCalcHashFromFileHandle` gives
  the same INF hash and `CryptEncodeObject` the same entry link; `WinVerifyTrust` (Authenticode, no revocation, no network) on the INF
  through the catalog returns only `0x800B0109` CERT_E_UNTRUSTEDROOT (hash and signature good, root not trusted on this PC), a changed
  INF returns `0x800B0100`; with the certificate as the only trusted root of an in-memory chain engine (`hExclusiveRoot`; no store of this
  PC read or changed) Windows' Authenticode chain policy returns 0. That a PnP install accepts it once the certificate is in Root and
  Trusted Publishers is **believed** (the documentation above and section 8's corroboration), not run here.

**The elevated step** (`DriverActionHost.cs`, `SystemDriverApi.cs`, `Elevation.cs` `RunasLauncher`, `DriverActions.cs` `DriverActionAdapter`):

- One driver change = one run of the same executable (the native single-file host's own path, or `ClassicCartStudio.exe`) started with
  `runas` and `--driver-action <request>`; both hosts handle that argument before any window, lock or single-instance check
  (`ccs-backup-utility/Program.cs`, `tools/desktop/ClassicCartStudio/Program.cs`). Nothing is extracted: no helper, no DLL, no copy of the
  program. Refusing the permission prompt is reported as "Windows did not give administrator permission"; an already elevated program is
  never told Windows will ask again (that Windows does not ask again is **believed**, not run).
- The request is base64url JSON in the command line (letters, digits, `-`, `_`), never a file: a program without administrator
  permission cannot change an elevated process's arguments, so nothing can be swapped between the window and the step, and no request file
  goes to AppData or anywhere else.
- **Setup:** refuses unless the request is Workbench's own plan of this version (INF hash, GUID, identity) and the PC, read again inside
  the step, still has nothing for the identity. Then: new working folder `%windir%\Temp\ccs-usb-driver-<random>` created new with access
  for Administrators and SYSTEM only; INF and catalog written and checked (`CcsCatalog.Check`); key destroyed; certificate added to Root,
  then Trusted Publishers; `WinVerifyTrust`; `DiInstallDriverW(flags 0)`. Any failure takes back this step's certificate by exact
  thumbprint in reverse order, but only while no package signed by it is on the PC (a package Windows staged anyway keeps its trust and the
  read-back decides). The folder is removed.
- **Removal:** refuses unless the published package is still exactly the recorded one (Workbench's INF bytes, the recorded catalog hash,
  signed by this operation's certificate, not pending removal) and used by no device instance the setup did not bind, and unless every
  certificate named is this operation's, keyless and the package's signer. Then `DiUninstallDriverW` (or `SetupUninstallOEMInfW` without
  `SUOI_FORCEDELETE` before Windows 10 1703). Windows' answer is not the result: before any certificate is touched the step reads the PC
  again (`TrustCleanup.Check`) and removes a certificate (exact store and thumbprint) only when the package is read back gone by its own
  published name, no device instance still names it, Windows reported no restart and no console device waits for one, every package
  catalog was read and none is signed with it, and the certificate is still exactly the one recorded (same subject naming the operation,
  same expiry, no private key). If the package is still there, its removal waits for a restart, or the PC cannot be read, **both**
  certificates stay and the step exits `0x4343000E` (restart needed) or `0x4343000D`; a certificate whose signer scan is incomplete or
  that signs another package stays and the step exits `CertificateKept`.
- **After the removal (deferred cleanup; `TrustCleanup.cs`):** the window reads back and records the setup's certificates still on the
  PC as a deferred cleanup (`DriverRecord.CleanupState = "deferred"`, `DeferredCertificates`, and whether a restart of Windows must be
  seen first: always, unless Windows reported a finished removal and the reading agrees). Its words never call a pending or lingering
  removal finished ("Windows needs to restart this PC to finish removing the USB driver ... The certificate added with it was kept until
  the removal is finished."; "Windows reported that it removed the USB driver, but the driver is still on this PC ..."). At the next
  start the records and the PC are read (only): the cleanup is offered only when the package is gone, a restart is seen where one is
  required (Windows' start time, `GetTickCount64`, later than the removal and not the start read then), the certificate has no other user,
  and it is one the setup added (listed as introduced, absent from the setup's own before-reading). Otherwise it stays and the start says
  why (a restart is still needed, the driver is still on this PC, a catalog could not be read, another package is signed with it, it
  changed). The question's default is "No - Keep Certificate" (recorded, never asked again); "Ask Me Later" records nothing. The cleanup
  is one more `--driver-action` request (`"cleanup"`), through the same adapter and the same closed boundary, and the elevated step checks
  everything again on its own reading (another operation's id, an unrelated or Hakchi certificate, a restart not seen, the package back:
  refused, nothing touched). A window or step that ends part way leaves the record open; the plan written before the step bounds what a
  later cleanup may ever remove. Inside Classic Cart Studio the cleanup is offered only at the app's own close (`DriverAtAppClose`), with
  the other console users still counted. These cleanup texts are engineering wording in the style of the owner's close dialog, not
  owner-approved copy.
- Exit codes (`DriverExit`): 0, 3010 (restart needed), `0x4343xxxx` for the step's own refusals, otherwise Windows' error, reported in
  Windows' words (setup errors from `setupapi.h` in plain words). The window still reads the PC back and decides from that.

## 11. Open items and owner decisions

1. **Activation.** The adapter is built and tested through its seams only. Opening `Gate.DriverChanges` is a reviewed code change and
   every actual setup or removal needs the owner's separate driver/UAC approval (W01, W15). No driver, certificate or store was changed
   on any PC by this work.
2. **The trust route is the owner's choice and is pending (section 12).** What is implemented (route a, per-setup self-signing with trust
   insertion) is narrowed (one certificate per setup, key in memory only and destroyed before trust, CA=false, Code Signing only, subject
   naming the operation, removed by exact thumbprint only once its package is read back gone) but it is a Local Machine Root entry, and
   Microsoft describes trust insertion to automate installation as an internal-test practice not to be used for packages distributed
   outside the organization. The alternatives (route b, a release-signed catalog; reuse of an existing compatible driver; no package) and
   their x64/Arm64 prerequisites are in section 12. Nothing here buys a certificate, opens an account or installs trust.
3. **Windows on Arm.** Section 12. In short: Microsoft requires WHQL-signed catalogs for release on architectures other than x86 and
   amd64; whether route a's self-signed catalog is staged on Arm64 is **unknown** here (upstream libwdi claims WinUSB installation on Arm64
   since 1.5.0); any driver change there needs the native Arm64 Workbench host, which is built but has never been executed. Arm64 stays
   unrun until hardware.
4. **Managed PCs.** Device-installation policies, WDAC or an administrator's certificate policy can refuse the package or the Root entry;
   the step reports it in Windows' words (for example "a policy on this PC does not allow setting up this device (error 0xE0000248)") and
   takes back what it added. Not observed here.
5. **Hakchi coexistence.** Hakchi 3.9.3 decides whether its driver is installed by finding `USB\VID_1F3A&PID_EFE8` in `pnputil -e`
   output (section 1), i.e. its signer name. Workbench's signer name does not contain that text, so Hakchi does not recognize Workbench's
   driver and runs its own forced setup, which rebinds the console to its package (Workbench's then sits unused and can still be removed;
   Hakchi's certificate deletion is by its own subject and does not touch Workbench's). Choosing a subject Hakchi would match is possible
   but imitates another tool's detection; left as an owner choice.
6. **Owning-host close in Classic Cart Studio.** An embedded Workbench never removes the driver (the app may use the console
   connection). Classic Cart Studio's own close asks instead (`MainWindow.OnClosingWindow` -> `BackupWorkspace.DriverAtAppClose`,
   **verified** in source): the removal question for a driver a Workbench window inside the app set up in that run, then the cleanup
   question for any certificate an earlier removal kept that the window found at its start, by the same rules with the app no longer
   counted as a console user.
7. **Certificates left behind.** A certificate a removal kept is a deferred cleanup (section 9). A certificate left by a *setup* step that
   ended part way (no package) is still only reported at every start and kept: Workbench offers no cleanup for it (a possible later
   extension, with the same reading rule; not built). Windows has no reliable read-only signal for a pending driver-store deletion
   (**unknown**), so where a removal's end was not confirmed Workbench requires a restart of Windows to be seen (Windows' start time read
   through `GetTickCount64`, later than the removal and more than two minutes from the start read then) before it offers a cleanup; only
   a forward clock change larger than both the time Windows had been running at the removal and two minutes could be mistaken for a
   restart (**believed** rare; the package-gone and no-user checks still apply). Microsoft OS descriptors on the clovershell gadget and the FEL/gadget instance identity remain **unknown** until
   a hardware or driver test is authorized.
8. Upstream libwdi has fixed several issues the pinned helper still has (infinite loop on a failed certificate delete, UAC test, a crash
   when signing fails, DLL side-loading hardening); see `UPSTREAM-RECHECK.md`. Workbench never runs that helper; the pin is unchanged.

## 12. Trust routes for Workbench's WinUSB package (the owner's choice; none is chosen here)

Three different things are each called "signing". They are separate decisions with separate evidence, and none of them is chosen by
this document. Microsoft Learn pages read November 16, 2026 (ms.date given): [Trusted Publishers Certificate Store](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/trusted-publishers-certificate-store)
(2022-03-18), [PnP Device Installation Signing Requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/pnp-device-installation-signing-requirements--windows-vista-and-later-)
(2022-03-03), [Driver Code Signing Requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-reqs) (2025-05-29),
[Attestation Sign Windows Drivers](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation) (2025-07-15),
[Driver Signing Options](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/driver-signing-offerings) (2026-03-23),
[Certificate Deprecation](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/deprecation-of-software-publisher-certificates-and-commercial-release-certificates)
(2025-07-11) and the [Artifact Signing FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq) (2026-05-14). No legal or
compliance opinion is made, and nothing was bought, opened, submitted or installed.

| Route | What it is | In Workbench |
|---|---|---|
| (a) per-setup self-signing with trust insertion | each setup makes its own certificate, signs the catalog with it and adds the certificate to Local Machine Root and Trusted Publishers (section 9) | implemented, closed by `Gate.DriverChanges`; Microsoft describes it as an internal-test practice |
| (b) release-signed catalog | Microsoft signs the catalog through the Hardware Dev Center (WHCP after HLK tests, or attestation) | not built; needs the owner's choice, an account, an EV certificate and a submission |
| (c) the app's own Authenticode signature | the Rance9 LLC signature on `CCS-Console-Workbench.exe` and `ClassicCartStudio.exe` | separate work (the app's signing setup); it does not sign a driver catalog |
| reuse | a compatible WinUSB association already on the PC (Hakchi's, Workbench's earlier own, another with an interface GUID) | implemented, reads only; never replaced or removed |

**(a) Per-setup self-signing with trust insertion.** Microsoft: "By installing the Authenticode certificates in the Trusted Publishers
certificate store, you can automate the installation of your driver package on various systems that are used for internal testing and
debugging." and, marked Important: "This practice of automating the installation of driver packages is only suggested for your internal
systems. This practice should never be followed for any driver package that is distributed outside your organization." libwdi (and so
Zadig and Hakchi's helper, section 3) use the same mechanism; that does not change the guidance. Workbench's narrowing (section 9) and
its trust cleanup (a certificate leaves only after its package is read back gone, else a deferred cleanup) limit what stays on a PC; they
do not make the route a release-signed one. Using it in a public build, or only for private/test use, is the owner's decision.

**(b) A release-signed WinUSB catalog.** Microsoft regenerates and signs the catalog ("Microsoft regenerates catalog files and replaces
any catalog files submitted previously"); the PC then needs no certificate change and there is nothing to clean up. Prerequisites:
- registration in the Windows Hardware Developer Program (Partner Center hardware dashboard) as an organization;
- "To submit binaries for attestation signing, your Hardware Dev Center dashboard account must have at least one EV certificate associated
  with it. This requirement is also true if you want to submit binaries for Windows Hardware Compatibility Program (WHCP) certification."
  The EV certificate comes from one of the listed certificate authorities; Azure Artifact Signing "doesn't issue Extended Validation (EV)
  certificates";
- a CAB signed with that certificate, holding the INF (and a catalog, which Microsoft replaces); "Each driver folder in your CAB file must
  support the same set of architectures". Workbench's INF is one data-only file with NTx86, NTamd64 and NTarm64 sections (section 9).
  Whether the dashboard accepts a package with no driver binary and no symbol file is **unknown**;
- the offering: WHCP (HLK-tested and dashboard-signed; Microsoft's recommended method, "it signs a driver for all OS versions", and the
  only one accepted by Windows Update for retail audiences and by Windows Server 2016 and later) or attestation (no HLK; "only works on
  Windows 10 Desktop and later"; requires the EV certificate; "When a driver receives attestation signing, it's not Windows Certified").
  In the 2026-03-23 revision the attestation section is titled "Attestation signed drivers for testing scenarios" and begins "For testing
  purposes only, you can submit your drivers for attestation signing". Whether an attestation-signed catalog installed by Workbench itself
  (not through Windows Update) remains acceptable for public use under that wording is **unknown**; which HLK tests, if any, would apply to
  a WinUSB package for a device Rance9 does not make (the console) is **unknown**;
- one signature per package version: "every time a Production level driver package is rebuilt, Microsoft must sign the package".
  Workbench's INF bytes are fixed (`CcsDriver.InfSha256`), so a new signature is needed only when the INF changes.
A commercial (non-Microsoft) release certificate on the catalog is listed by the PnP page as acceptable for staging on x86/amd64
("signed by WHQL or signed by a third-party release certificate"; Windows then asks unless the publisher is trusted), while the 2025
certificate FAQ answers "all production driver packages must be submitted to, and signed by Microsoft". The two pages disagree for this
case; it is **unknown** for an INF-only WinUSB package and was not tested. Arm64 excludes it (below).

**(c) The app's own signature.** Signing the executables with the Rance9 LLC identity gives Windows a verified publisher for the program
and its administrator prompt. It is not a driver catalog signature: the Artifact Signing FAQ says "Signing with the Partner Center is
kernel-mode signing ... Sign your user-mode binaries by using Artifact Signing." Whether a catalog signed with an Artifact Signing
profile would be accepted by device installation is **unknown** and outside that service's documented scope (it would be the third-party
release case of route b). App signing never stands in for (a) or (b).

**Reuse.** Whatever route is chosen, `DriverSetup.Assess` reads the PC first and reuses a compatible association with no driver or
certificate change (section 7). On this PC the read-only `driver-real` group (November 16) assesses `PinnedHakchi`: the owner's
Hakchi-installed package is the association Workbench would use, and it would be left in place.

**Prerequisites by Windows architecture** (what Windows requires to install a WinUSB catalog for Workbench's INF):

| | x64 (Windows 10/11 desktop) | Arm64 (Windows 11 on Arm) |
|---|---|---|
| Program that runs the step | the x64 standalone host or Classic Cart Studio for Windows, as a native 64-bit process (`DiInstallDriverW` refuses a 32-bit process on 64-bit Windows, `ERROR_IN_WOW64`) | the native Arm64 standalone host (.NET Framework 4.8.1's Arm64 runtime; `native-host/NATIVE-HOST.md`): built, never executed. The x64 host under emulation refuses ("an x64 program on an Arm-based PC", `WindowsSystemDriverApi.NotNative`); that `DiInstallDriverW` refuses an emulated process is **believed**. Classic Cart Studio for Windows on Arm is not established here |
| Route (a) | administrator permission; Root and Trusted Publishers additions allowed by the PC's policies; no test-signing boot option, since the package carries no kernel binary (`winusb.sys` is Windows' own) — **believed**, corroborated by the owner's libwdi-signed Hakchi package staged on this PC on 2026-10-09 (read only). | A third-party release certificate | listed as acceptable by the PnP page, contradicted by the 2025 FAQ: **unknown** | not accepted ("signed by WHQL" only) |

Whichever route the owner chooses, the cleanup rule stays: Workbench removes only a certificate it demonstrably added, only after its
package is read back gone and nothing else uses it, and never by subject. Route (b) and reuse add no certificate, so there is nothing to
clean up.
